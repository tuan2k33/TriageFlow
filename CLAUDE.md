# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

Crawl every issue and PR (open and closed) of a GitHub repository into SQLite, text and metadata only, **never code or diffs**; then sort them into categories, suggest labels from the repo's own labels, find duplicates, already-fixed issues and competing PRs, and write a report and an HTML page to browse. From the crawl to the report it is data analysis and classic machine learning only (local embeddings, KMeans, kNN, vote counts, rules learned from titles); **no LLM in any step** (earlier LLM steps were removed at the user's request; do not add them back). The one exception is `tools/llm_judge.py`: the user wanted a free OpenRouter model to recheck the report's rows to save checking by hand; it sits outside the pipeline, only writes `judge.jsonl`, and the report merely shows its verdicts. Goals, scope and the state of each part are in `GOAL.md`; read it before adding features. Test repos: `numpy/numpy` (33k items) and `tqdm/tqdm` (1.8k items, a full crawl is about 90 requests, good for quick tries).

## Commands

Needs `gh` logged in (the crawler takes the token from `gh auth token` and stores it nowhere). The project venv only has datasette; `torch`, `transformers`, `sklearn`, `numpy` come from the shared env `~/.dev/venv` (through the `_base_env.pth` that `mkproj` writes), so they are not in `requirements.txt`.

`python run.py <repo link or owner/name>` runs crawl, analyze, report and build_html in order (`--labels` adds `suggest.py`; label suggestions and the LLM recheck are optional steps, kept out of the end-to-end flow at the user's request) and prints the paths of `repo.db`, `browse.html`, `report.md`, `actions.sh`. `python web.py [port]` starts a local web view (listens on 127.0.0.1 only): a paste-a-link box that runs `run.py` and shows its log, and four pages per repo: Browse (`browse.html` in an iframe), Report, Actions, Database (`repo.db` read-only, with an SQL box). Step by step, run **one after another**; each step can be rerun and only does what is missing:

```bash
R=data/numpy__numpy/repo.db
python triageflow.py numpy/numpy   # crawl; --full starts over, --review-comments adds inline review comments (off by default)
python analyze.py $R               # embed new or changed items; first run (or --init) makes the categories, later runs put new items into them
python suggest.py $R               # optional: type labels (title rules, then kNN) and component labels (title rules, then votes); sweeps neighbors x votes, prints held-out accuracy
python report.py $R                # actions table + report.md and actions.sh next to repo.db (every gh command commented out)
python build_html.py $R            # -> browse.html next to repo.db
datasette $R                       # browse and run SQL
```

`python -m pytest tests -q` runs the offline checks (a few seconds, no network or model): a synthetic repo with planted duplicates, zombies and competing PRs goes through analyze, suggest, report and build_html; plus the link regexes. Checks on real data:
- `suggest.py` always prints accuracy: the type axis by leave-one-out, the component axis over the whole (neighbors, minimum votes) grid on a balanced sample (600 items with a component, 600 without), rescaled to the repo's real share. `--eval-only` measures without writing.
- After a crawl, compare `select sum(comments) from items` with the number of `comments` rows with `kind='comment'`; under 1% off is normal (comments deleted or added during the crawl), a large gap means the crawl was cut short.
- Category assignment: delete a few `topics` rows of open items and rerun `analyze.py`; they must land in the same category.
- The JS in `build_html.py` is a Python string: after editing it, rebuild a page, extract its `<script>` to a file and run `node --check`.

## Architecture

One SQLite file per repo, `data/<owner>__<name>/repo.db` (`data` is a symlink to `~/.dev/data`, outside git). Each script reads the DB and writes its own tables:

| Table | Written by | Notes |
|---|---|---|
| `items` | triageflow | every issue/PR in every state (`state`, `state_reason`, `merged`); `labels` is a JSON array (label names may contain commas); `state='deleted'` for items deleted or transferred (`reconcile` compares the open list with GitHub on every crawl) |
| `comments` | triageflow | key `(kind, id)`; `kind='comment'` (conversation) or `review_comment` |
| `links` | triageflow | from GraphQL: `closes_official` (PR closes issue, read from both the PR and the issue side, so abandoned PRs are included), `duplicate_of` (duplicate → original), `sub_issue` (child → parent); from text: `closes` / `mentions`, matching `#N`, `gh-N` and full same-repo URLs (only numbers present in `items`) |
| `fts` | triageflow | FTS5 over titles, descriptions and comments; rebuilt every time |
| `meta` | triageflow, analyze, suggest | `repo`, sync marks `*_since` and ETags `*_since_etag`, `category_threshold`, `calibration` |
| `emb` | analyze | a 384-dim FP16 vector for **every** item: the mean of the title + description embedding and the embedding of a digest of the whole thread (`digest.py`), both at 512 tokens; with a `hash` of title, description and comments, so new, edited or newly commented items are re-embedded |
| `categories` | analyze | made **once** at init: name, size, centroid (normalized) |
| `topics` | analyze | the category of **every** item (`-1` = Unsorted, when farther from every centroid than the threshold) |
| `neighbors`, `similar` | analyze | the 5 most similar items of each item; `similar` = semantic links, pairs in each other's top 5 (`rank` 0 = each other's nearest); recomputed every run |
| `pr_status` | analyze | each open issue: `merged` / `open` / `abandoned` / `none` by the PRs that close it (`closes_official`, `closes`), or `tracking` if it has sub-issues; recomputed every run |
| `dup_pairs`, `dup_master` | analyze | candidate duplicate issue pairs by level `github` / `likely` (cosine ≥ `DUP_SIM` 0.92) / `possible` (each other's nearest); `dup_master`: the issue to keep for each issue |
| `zombie`, `pr_compete` | analyze | open issues that a later merged PR seems to fix without a link (`ZOMBIE_SIM` 0.88, each other's nearest); pairs of open PRs closing the same issue or very similar by different authors |
| `actions` | report | every proposal: `kind`, `number`, `target`, `confidence` (0-1), `reason`, `command`; recomputed every run |
| `suggested` | suggest | numpy: `axis` `type` / `component`, `source` `title` / `knn` / `vote`; other repos: `axis` `label` (`vote`); `share` = votes / possible votes; recomputed every run |

Things that only show up across several files:
- **Open and closed:** raw data, `emb` and categories cover every state (kNN and votes also use closed items); suggestions and the HTML page are for open items only.
- **Number of categories:** k = sqrt(open items), clipped to 8-60 (numpy 47, tqdm 26, pypa/wheel 8). The embedding has no natural number of clusters (numpy: silhouette ~0.05 and seed agreement ARI 0.4-0.65 for every k from 8 to 150, inertia without an elbow), so k is a reading choice, and deep or density clustering would not create structure that is not there (HDBSCAN put half the items in one cluster). Re-clustering only rewrites `categories` and `topics`: on numpy the 1597 `actions` rows were identical before and after. Categories group by content and do **not** map to labels: the embedding has no clean clusters (AMI with component labels about 0.27; centroids of component labels are closer to each other than members are to their own centroid); KMeans converges but two seeds agree only ARI ≈ 0.6, so re-clustering reshuffles a lot. Label suggestion does not use categories. Names are generated (`distinctive_names`: the most over-represented label plus the 3 most distinctive title words); the user likes the grouping, keep it.
- **Type kNN** (`suggest.py`, `K=10`, suggested at score ≥ 0.5): tuned on the current embedding, K=3/5/10 give coverage / precision 0.85/0.84, 0.82/0.86, 0.79/0.88; K ≥ 15 is no better. Re-tuning the component vote, other (KC, m) pairs (7 and 3, 10 and 3) lie on the same trade-off curve as 5 and 2, so 5 and 2 stay.
- **Title rules** (`suggest.py`, numpy mode): a prefix such as `BUG:`, `ENH:` → type label, and a component's name in the title (`f2py`, `np.ma`...) → component label. Rules are learned from labeled items (not hard-coded) and kept only if right ≥ 85% on ≥ 20 items. numpy: prefixes cover 72% of items at 96% (kNN on the same items 90%; where they disagree the prefix is right 93%, kNN 25%), so the prefix comes before kNN; together 93% coverage at 93% (kNN alone 79% / 88%). Component names keep 10 rules (CI, SIMD, f2py, linalg, ma, random...), measured on items that have a component label; `build`, `dtype`, `ufunc`, `documentation` are dropped as too generic.
- **Component votes** (`suggest.py`): the number of neighbors and the minimum votes are swept per repo over `KC_GRID` x `M_GRID`, keeping the pair that finds the most with exact-match precision ≥ `TARGET_PRECISION` 0.5 (the user's choice: on numpy the old 5 neighbors / 2 votes measured 0.49 exact and ~88% related by hand); numpy now gets 15 neighbors / 4 votes (finds 0.72 at 0.51), on the same trade-off curve. In generic mode the number of neighbors is swept the same way (most right suggestions over the kept labels). Each of the K most similar labeled items gives one vote to each of its components, linked items add theirs (`closes_official` 3, `closes` 2, `mentions` 1); every component with 2 votes is suggested, so an item can get several. Tried and dropped: weighted mix with keyword naive Bayes (one label only, finds 56%), a sphere (centroid + radius) per label (labels overlap in the embedding, precision ~0.2-0.3), K=5 ≥1 vote (74% of items without a component get one), K=7 ≥3 votes (surer but finds only 63%). Exact-match precision (0.50) is a lower bound: of 50 hand-graded "wrong" labels 77% were still related, i.e. about 88% of suggested labels are related; use the automatic numbers only to compare rules.
- **Stable categories:** only init runs KMeans; later new items go to the nearest centroid (cosine), so categories do not move. `--init` to redo them.
- **Type × component matrix** (Matrix button in `browse.html`, asked for by the user instead of a map): rows are type labels, columns component labels (a repo without such labels gets pseudo labels: last-activity buckets as rows, content categories as columns), cells the open items; size = count, color = share quiet for 3+ years, dashed = some items are there only through a suggested label. An item with several labels counts in every cell. Computed in JS from the page's data, following the active filters; clicking a cell filters the list.
- **No map:** t-SNE 2D/3D projections were built and then dropped by the user (the embedding has no clean clusters, so the picture says nothing); do not add them back. `browse.html` is self-contained (plain JS, data embedded as JSON): filters, the list of open items, details with a timeline (closed items included, up to 60), an overview reading the `actions` table.
- **Text links:** numpy writes `gh-1234` and pastes URLs more than `#1234`; matching only `#N` missed 25% of pairs. "fixes #N" counts as `closes` only in the item's own title or description; in comments it is `mentions` (numpy: GitHub confirms 69% of such phrases in PR descriptions, only 1% in comments).
- **Comments are worth their crawl cost** (3/4 of the requests): 31% of references appear only in comments, and 71 of the 77 duplicate pairs GitHub records are mentioned only in comments.
- **The embedding reads the whole thread** through `digest.py`: title, description and non-bot comments, without code, tracebacks, quotes, links and `#N`; a thread that fits 500 tokens is kept whole (numpy: 26k of 33k items), a longer one keeps its title and first sentence and fills the rest by MMR (maintainers' sentences and sentences with "fix", "duplicate"... get a bonus). No model writes text: every sentence comes from the thread. Vector = mean with the title + description embedding. Measured on numpy's GitHub links (rank of the right answer): duplicate → original first 47% (title + description at 256 tokens: 36%), issue → its merged closing PR 41% (34%). The digest alone did not help duplicates (comments drift to other topics), hence the mean. Hand-graded after the switch (description and maintainer comments read, numpy): duplicates ≥ 0.92 ~79% the same problem (24 pairs), zombies 10/20 fixed and 6/20 partly, type labels with K=10 20/30 right and 5 arguable. Re-embedding all of numpy takes about 8 GPU minutes.
- **Thresholds depend on the embedding:** after changing the embedding, re-measure `DUP_SIM` (matching the pair count of the old embedding is only a starting point; grade by hand: the new embedding at 0.91 had the same count but ~54% right, ≥ 0.92 ~79%), `ZOMBIE_SIM` (the zombie rule on closed issues with a known closing PR: how often the matched PR is one of them) and kNN `K`; categories need `--init`.
- **Semantic links** use a relative test (mutual top 5) because no absolute cosine cut separates them; they feed the timeline and duplicate grouping. Giving mutual neighbors more weight in the component vote was tried: no gain, only a move along the same trade-off curve.
- **Duplicate grouping** pairs issues with issues only and never chains pairs (chaining made one group of 151 issues). The embedding is the only signal: title word overlap, function names, same author and a logistic regression over 5 signals did not rank the original better than cosine (first 39%, top 5 59%, top 30 78%).
- **Report layout (the user edited `report.md` by hand on 2026-11-17; the edits are now in `report.py`):** the top has only "How this report is made" (5 steps: Crawl repo, Read and trim, Compare and group, Suggest label, Score and check) and "Tech used" (no numeric thresholds, only "high similarity", "nearest"). No "How to read it" section. Each section is then only its title and an HTML table inside `<details>` (folded by default; no blank lines inside the HTML block, or VS Code's markdown-it cuts it), columns 30/20/50: Item / Proposal (confidence) / Check, widths set both in `<colgroup>` (VS Code) and on the header cells (GitHub drops colgroup and style). Confidence in brackets: `1.00` only when a maintainer marked the duplicate; anything an algorithm decides is at most 0.99. The Check column has no prefixes: the hand check (`manual.jsonl`) first, then the LLM (`judge.jsonl`); marked duplicates say "checked by maintainer". No level column, no per-row percentage derived from samples.
- **Never overwrite hand edits:** `report.md` is regenerated on every run. `report.py` stores the SHA-1 of what it wrote (`.report.md.sha1`); if the file on disk differs, it is copied to `report.md.edited-<time>` before being rewritten. When the user edits `report.md`, port the change into `report.py` (diff the backup against a fresh run) instead of dropping it.
- **A duplicate of a closed issue is not a close proposal:** `report.py` makes it `check_recurrence` (the command is only `gh issue view`), because the old bug may have come back. Only when the original is still open is closing the newer one proposed.
- **Suggestions never touch real labels** or GitHub: they live in their own table and the HTML page shows them dashed. Keep it that way.
- **GitHub API:** the `GitHub` class in `triageflow.py` calls REST/GraphQL with `urllib`: sleeps near the rate limit, retries on 5xx and network errors, pages by the `Link` header. `stream()` sorts by `updated` ascending and stores the last `updated_at`, so a cut-off run resumes where it stopped; the first page's ETag is stored with the `since` it used, so a sync with nothing new gets a 304 (free).
- **Published output:** the repo is public at github.com/tuan2k33/TriageFlow (branch `master`). `reports/numpy__numpy/` holds copies of numpy's `report.md`, `browse.html`, `actions.sh`, `judge.jsonl`, `manual.jsonl` (no `repo.db`: 370 MB); after regenerating, copy them there again.

## Notes

- GitHub silently stops every listing at 300 pages (30,000 rows at 100 per page). `stream()` continues from the last mark; do not remove that part.
- The `pulls/comments` endpoint often answers 502 on large repos, so inline review comments are off by default. Review bodies (approvals with remarks) are not crawled.
- SQLite allows one writer: never run two writing steps on the same DB at once (`database is locked`).
- Rate limit: GitHub 5000 requests per hour (GraphQL counted separately).
- **Two label modes** (`suggest.py`): a repo whose labels match `AXES` (numpy) gets types by title rules then kNN, components by title rules then votes. Other repos go to `generic()`: every label in use is a candidate, each with its own minimum vote count, the smallest (2..10) at which the hidden-label test is right ≥ 50% on ≥ 10 tries; labels that never get there are never suggested (on tqdm, process labels such as `need-feedback`, `to-review`, `duplicate` drop out by themselves). The thresholds are picked on the same sample, so the numbers are a little optimistic. By default every open item missing a type or a component gets suggestions (`--unlabeled-only` limits it to items with no label). No new labels are ever made up.
- Issue-side GraphQL (`issue_links`): 100 issues per query, about 3 rate-limit points; all of numpy is 142 queries, ~9 minutes, later runs only fetch changed issues. The "marked as duplicate" event sits on the timeline of the **original** issue, so read both `duplicate` and `canonical`. Cross-references (`CROSS_REFERENCED_EVENT`) were tried and dropped: GitHub answers 502 or RESOURCE_LIMITS_EXCEEDED even at 25 issues per query; the `#N` regex covers them.
- Small repos are real edge cases: `pypa/wheel` has only 26 open items and once broke the (now removed) map step. After changing `analyze.py`, try `python run.py pypa/wheel` (full crawl about 50 requests, 1 minute).
- Staleness (last activity within 1 / 1-3 / 3-5 / over 5 years) and the overview are computed in the page's JS, with no table of their own; the overview reads `actions`, so run `report.py` before `build_html.py`.
- When stopping background runs use patterns anchored with `^` (`pgrep -f "^python -u triageflow.py"`); an unanchored `pkill -f` also matches the shell typing it.
